# Embedding 阻塞与 Milvus 锁范围修复

## 修改前的两种等待

1. 长期记忆的 add/search 虽然是 async def，但直接调用同步 embed()。真实适配器内部使用同步 httpx.Client，网络等待发生在事件循环线程；等待期间同一线程上的其他请求无法得到正常调度。旧记忆缺少向量时的补填也有同样问题。
2. Milvus 原本通过 asyncio.to_thread 将整个操作放到工作线程，事件循环没有被这个操作直接阻塞；但工作线程先拿同一个 RLock，再执行整份文档的逐片 Embedding、insert，或查询 Embedding 和 search。其他访问该知识库的工作线程只能等锁。两者是不同问题：前者是事件循环阻塞，后者是共享锁竞争。

## 修改后

长期记忆的新增、查询、旧记录补填，三处都改为 await asyncio.to_thread(embed, text)。异步调用者等待自己的结果，同时事件循环可以调度其他协程。仍使用已有 Embedding 同步适配器和网络超时，没有改变模型与向量语义。

Milvus 上传改为：

```
短暂持客户端锁：检查初始化和 Schema
释放客户端锁
工作线程：切分、逐片 Embedding、校验向量、准备全部记录
短暂持客户端锁：insert；失败时尝试清理该 doc_id
```

检索改为：

```
短暂持客户端锁：检查初始化
释放客户端锁
工作线程：query Embedding
持客户端锁：BM25 + 向量查询 + RRF
```

锁仍保护 SDK 访问、初始化和 close，避免未经验证就允许共享客户端任意并发。这里的“短暂”是相对去掉远程 Embedding 而言：数据库慢请求仍会持锁，SDK 超时仍然有效，并不保证固定持锁时长。两路数据库查询仍串行。

模型版本/Schema 检查在付费向量化前进行；所有向量准备并校验完成后才开始写入。原有失败写入补偿仍保留。未添加新的数据库字段，不需要重建 Collection。

## 验收方式

tests/test_embedding_concurrency.py 使用 threading.Event 控制假的同步 Embedding，在外部释放之前保持等待，避免把偶然的耗时变化当性能证据：

- 新增记忆、查询记忆、旧向量补填均验证在工作线程执行；等待期间另一项异步数据库读取能够完成。
- 上传 Embedding 等待期间，文档列表和另一条检索能完成；未准备完成的新文档不可见。
- 某条查询 Embedding 等待期间，其他查询可继续。
- 在上传向量准备期间取消请求，不会继续进入 insert。

tests/test_milvus_integration.py 在真实 Milvus 的独立随机 Collection 中验证：上传停在可控慢 Embedding 时，已有文档仍能检索；释放后新文档正常入库。模型为本地 Hash，仅验证并发与真实数据库协议，不是付费模型速度或语义效果测试。测试结束清理其临时 Collection。

## 边界

- to_thread 不会加速单次模型推理；它让网络等待不占事件循环线程。
- 取消 await 不能强制停止已经运行的工作线程或 HTTP 请求。准备阶段取消后不启动 insert；如果取消发生在已经提交的 SDK 写入阶段，仍可能完成写入，不能宣称事务回滚。
- 默认线程池容量有限，大量请求仍可能排队；尚未增加独立线程池、批量 Embedding、限流或后台任务队列。
- 文档上传层仍有独立的文件锁，串行化上传/删除以保护上传回执；普通检索不需要该文件锁。
- 本次没有修改排序参数、评测标签、模型选择或引入新的第三方框架。
